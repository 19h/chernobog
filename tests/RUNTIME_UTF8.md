# Runtime UTF-8 recovery

Runtime final-memory consensus now admits UTF-8 text using the existing shared
scalar decoder. ASCII continues to work. Payloads require a captured NUL,
at least four Unicode scalar values by default, and at most 4,096 encoded bytes
before the terminator. ASCII and C1 controls are excluded from payloads.

The decoder rejects invalid continuations, truncated sequences, overlong forms,
surrogates, and values above U+10FFFF, consistent with the encoding definition
in [RFC 3629, sections 3–4](https://www.rfc-editor.org/rfc/rfc3629.html#section-3).
The text-admission control filter is an additional project policy. No Unicode
normalization occurs: canonically equivalent strings with different bytes do
not satisfy consensus.

At each address, every eligible memory-observable run must supply the same
terminated prefix. Empty, invalid, unterminated, or conflicting duplicate records
veto that address. Records from ineligible runs and non-image memory are excluded.
Bytes following the first NUL are outside the prefix fact, as before.

Matching loaded, undefined IDB bytes receive an explicit UTF-8 string type.
Dummy labels generated by dynamic drefs are allowed for this exact-byte string
projection; real user/analysis names and comments anywhere in the range remain
protected. Runtime memory is not copied into the database. The same candidates
reach transient ctree literals through the existing display projection.

Projection lifecycle corrections clear the pipeline flag when its projection
is abandoned and seal the owned projection before the final ctree lookup.
Existing byte/topology/mutation checks remain in effect; this ordering admits
late Hex-Rays prototype refinement without turning display facts into fresh
branch or solver evidence.

## Assumption register and bounded scope

- U1: Valid UTF-8 and repeated bytes are sufficient for a candidate display
  string, not proof of textual intent or universal behavior. Independent seeds
  are concrete witnesses. Non-Latin examples, supplementary scalars, malformed
  inputs, absent runs, and conflicting records test admission. Medium impact:
  international text is now available to the runtime display path; binary data
  can still coincidentally satisfy the admission rules.
- U2: Length bounds refer to Unicode scalars and encoded bytes, not grapheme
  clusters or display columns. Tests distinguish a single four-byte emoji from
  four characters and exercise exact byte-cap boundaries. Low impact limitation:
  combining sequences count as multiple scalars.
- U3: IDB string creation requires byte-exact loaded data and an otherwise
  undefined range. The live fixture tests dummy labels, a preserved named range,
  an interior comment, and unchanged destination bytes. Medium impact:
  existing annotations remain authoritative.
- U4: A display projection belongs to the current synchronous decompilation.
  The fixture tests first and repeated uncached decompilation without pre-seeding
  a function prototype, then edits a consumed decoder key and verifies that the
  old literal disappears. Medium impact: stale context must cause renewed
  analysis rather than reuse of the previous literal.
- U5: Live validation below covers the local IDA 9.4 ARM64/macOS configuration.
  Standalone x86-64 tests cover the pure evidence path; they do not establish
  Windows/Linux IDA integration or GUI font rendering. Runtime UTF-16/UTF-32
  recognition remains outside this change because final-memory records do not
  supply an authoritative code-unit width.

Prefix validation takes O(P) time and O(P) decoded storage for P payload bytes.
With W eligible final-memory records, A distinct addresses and R run identities,
ordered-map consensus bookkeeping takes O(W(log A + log R)) lookups plus bounded
string parsing/comparison. No speedup is claimed for this capability change.

## Reproduction

Build the current plugin and run its CTest targets, then compile the benign
fixture and use an isolated raw-input IDA process:

```sh
cmake --build build
ctest --test-dir build --output-on-failure
cc -O1 -fno-builtin tests/runtime_strings/utf8_fixture.c -o /tmp/chernobog-utf8-fixture
python3 tests/run_ida_smoke.py \
  --ida /path/to/IDA-9.4/idat \
  --plugin /path/to/chernobog.dylib \
  --enable-rax --verbose \
  --output-dir /tmp/chernobog-utf8-validation \
  /tmp/chernobog-utf8-fixture tests/ida_runtime_utf8_smoke.py
```

The output directory must be new or empty. The runner records input and plugin
SHA-256 values and requires the probe's PASS marker. The probe also writes
`utf8_pseudocode.txt`. Its observed first-decompilation call is:

```c
return puts("Grüße 世界");
```

On 2026-09-08, the default-analysis run in `/tmp/chernobog-utf8-smoke-05` passed
with four observable runs, four consensus strings, one C-string argument literal
on each of the first two uncached decompilations, and one explicit UTF-8 IDB
string. The name/comment preservation, no-byte-patching, and changed-key
invalidation assertions also passed. Provenance:

- Fixture SHA-256: `394dc8bdd2845d7ed35cd493f8ca1d3c7deea3ed0b3c4ac412596560e479782b`
- Plugin SHA-256: `eb9c18c196237efb0c9c45d2c59e219c899c12c9f8c4cce00058a3f54265b6b0`
- Build source fingerprint: `a594f4a3c5da`; SDK `940`.

The full native build and all six CTest entries passed (1.65 s in the final
run). The standalone evidence suite, including UTF-8 cases, passed AddressSanitizer,
UndefinedBehaviorSanitizer, and x86-64 execution. `CHERNOBOG_LEGACY_EVIDENCE`
excludes these new consensus tests when reproducing older capture benchmarks.

A subsequent integration run on the same date, after the bounded libc models
and indexed-load correction, passed every UTF-8 smoke assertion again at
`/tmp/chernobog-libc-indexed-utf8`. It used plugin SHA-256
